## 1. Implementation summary

V2.2 splits **accept** from **marketplace finalization**:

- **Intent** (`acceptance_funding_intents`) + **payment** (`engagement_escrow_payments` with nullable `engagement_id`) created at prepare.
- On-chain **authorized** escrow create + fund; server verifies views/RPC.
- **`finalize_acceptance_after_funding`** (service_role) is the only path to accepted response, assigned request, active engagement, and provider notifications.
- Frontend: two-step confirm, status phases, resume on reload (`accept-response-form.tsx`).

**Invariant (code review):** No accepted response / active engagement without `funding_verified` + payment `funded` + finalize RPC. Client cannot call finalize or progress RPCs (after grant fix below).

## 4. Database state transitions

```
open request + pending response
  → prepare_acceptance_funding
  → awaiting_wallet (response still pending, request open)
  → create_submitted / fund_submitted (still not accepted)
  → funding_verified + payment funded (still not accepted)
  → finalize_acceptance_after_funding
  → response accepted, others rejected, request assigned, engagement active, payment.engagement_id set
```

## 8. Security review (§4)

| Control | Status |
|---------|--------|
| Authorized create only | **OK** (contract + sandbox) |
| Requester = predecessor | **OK** (contract tests) |
| Auth binds all funding fields | **OK** (shared message + contract) |
| Nonce replay | **OK** (contract test) |
| Signer key server-only | **OK** (not `NEXT_PUBLIC_*`; used only in server actions) |
| `accept_response` for authenticated | **Revoked** (v22 migration) |
| `finalize_acceptance_after_funding` | **service_role only** (verified) |
| `record_acceptance_funding_progress` | **service_role only** (verified) |
| `prepare_acceptance_funding` | Requester auth + row locks (code review) |

### Findings

1. **HIGH (fixed in migration `20251107221000`):** `record_engagement_payment_progress` and `record_engagement_settlement_progress` were executable by `authenticated` / `anon` after V2.1 `CREATE OR REPLACE` (Supabase default grants). Accept path uses separate RPC, but post-accept engagement funding could be DB-forged. **Revoke added.**

2. **V2.1 items still open** (see [v2-release-readiness.md](./v2-release-readiness.md)): **C1** wallet/network alignment for testnet, **H1** verify config vs frozen payment row, **H3** wallet link message binding, **H4** open create spam on old deployments, **M5** stuck releasing, etc. None re-open `accept_response` bypass; C2 remains fixed.

3. **Engagement page funding** (`prepare_engagement_funding`) still allows funding **after** engagement exists — redundant for V2.2 happy path but not an accept bypass.
