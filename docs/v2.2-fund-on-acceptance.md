# V2.2 — Fund on acceptance

## Overview

Accepting a provider offer **does not** immediately accept the response or create an active engagement. The requester must **fund escrow on-chain**; PaidAid verifies the chain (RPC + contract views) and only then finalizes marketplace state.

Direct `accept_response` for authenticated users is **disabled**. Acceptance uses `prepare_acceptance_funding` → wallet txs → verified finalize.

## Lifecycle

### Stage A — Prepare (Supabase)

RPC: `prepare_acceptance_funding(request_id, response_id, escrow_contract_id, chain_id, auth_nonce, auth_expires_at)`

- Authenticated **requester only**; request locked `FOR UPDATE`.
- Selected response must be **pending**; request **open**.
- Creates `acceptance_funding_intents` + `engagement_escrow_payments` (`engagement_id` null).
- Pre-assigns `planned_assignment_id` / `planned_engagement_id` for on-chain `engagement_id` binding.
- **No** accept, assign, engagement, provider hire notifications.

### Stage B — Wallet

1. Server signs `create_escrow_with_authorization` (`NEAR_ESCROW_FUNDING_SIGNER_PRIVATE_KEY`, server-only).
2. Requester signs create, then fund (native or NEP-141 per response asset).
3. Server actions `reportAcceptanceCreateTx` / `reportAcceptanceFundTx`:
   - Resolve tx via NEAR RPC where possible.
   - **View escrow**; `assertEscrowRecordMatchesFunding` / `assertFundingCompleteOnChain`.
   - Update intent via `record_acceptance_funding_progress` (**service_role**).
4. On verified funded: `finalize_acceptance_after_funding` (**service_role**) → `accept_response_with_ids`.

### Intent statuses

| Status | Meaning |
|--------|---------|
| `awaiting_wallet` | Intent created; no verified on-chain progress |
| `create_submitted` | Create tx verified; escrow exists (may be unfunded) |
| `fund_submitted` | Fund tx reported (intermediate) |
| `funding_verified` | On-chain **Funded** verified; finalize pending |
| `finalized` | Marketplace accepted; engagement active |
| `failed` | Terminal error |
| `expired` | Auth / intent expired |

UI maps these to confirm → wallet → verifying → success / retry (`accept-response-form.tsx`).

## Contract authorization

- Only `create_escrow_with_authorization` (legacy `create_escrow` panics).
- Canonical message: `PAIDAID_ESCROW_FUND_AUTH_v1` fields (contract, network, engagement_id, requester, provider, asset, amount, nonce, expiry).
- Requester must be transaction predecessor; ed25519 verify against contract `authorized_signer`.
- Nonces consumed once; expiry enforced.

See `contracts/escrow/src/authorization.rs` and `packages/shared/src/escrow-authorization.ts`.

## Assets

- **Native NEAR:** `deposit_native` after authorized create.
- **NEP-141:** `ft_transfer_call` to escrow with escrow id in message (engagement page + accept flow share wallet helpers).

Sandbox integration (`pnpm sandbox:test-escrow`) exercises **native** path end-to-end (create, fund, release, refund). Contract unit tests include NEP-141 scenarios; full FT sandbox script is not yet automated.

## Verification rules

- Tx hash storage alone is **never** sufficient.
- Failed execution on RPC rejects; ambiguous RPC may fall back to escrow view for fund step (same as V2.1 engagement funding).
- Payment rows store frozen `escrow_contract_id`, `chain_id`, amounts, and NEAR account ids — verified against on-chain record.

## Recovery

- `loadActiveAcceptanceFundingForResponse` on page load / focus.
- **Continue funding** resumes in-flight intent without a duplicate prepare when one active intent exists.
- `syncAcceptanceEscrowFromChain` / `reconcileAcceptanceFinalization` if DB lags after on-chain success.
- Idempotent finalize returns existing `planned_engagement_id` if already finalized.

## Environment variables

| Variable | Where | Purpose |
|----------|-------|---------|
| `NEXT_PUBLIC_NEAR_NETWORK_ID` | Browser | Default **localnet** |
| `NEAR_ESCROW_CONTRACT_ID` | Server | Escrow account for prepare |
| `NEAR_RPC_URL` / network config | Server | Verification |
| `NEAR_ESCROW_FUNDING_SIGNER_PRIVATE_KEY` | Server only | Funding authorization |
| `SUPABASE_SERVICE_ROLE_KEY` | Server only | Progress + finalize RPCs |

After `pnpm sandbox:deploy-escrow`, copy signer from `.sandbox/escrow-funding-signer.json`.

## Local setup

```bash
supabase start
pnpm db:reset
pnpm sandbox:start && pnpm contract:build && pnpm sandbox:deploy-escrow
```

Manual journey: [v2.2-acceptance-localnet-checklist.md](./v2.2-acceptance-localnet-checklist.md).

## Known limitations

- No cancellation/refund product flow (contract `refund` not exposed in app).
- **Testnet/mainnet:** wallet module defaults remain localnet-shaped (V2.1 **C1**).
- **Browser E2E** suite not in repo; manual demo required for full two-user journey.
- Post-finalize **engagement page funding** block still exists for legacy/alternate prep; V2.2 accept path funds before engagement exists.
- 72-hour auto-complete is off-chain eligibility only (no auto on-chain release).
